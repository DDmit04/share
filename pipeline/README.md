# Пайплайн скрапинга

Одна команда проходит по нескольким площадкам и собирает **два** итоговых файла:
`processed.xlsx` (найденные подшипники) и `unprocessed.xlsx` (то, что не нашли).

## Запуск

Из корня проекта:

```
.venv\Scripts\python -m pipeline.run --input data.xlsx --out results
```

Полезные варианты:

```
python -m pipeline.run --list-sites                  # какие площадки известны
python -m pipeline.run --sites bergab.ru,etm.ru      # только выбранные
python -m pipeline.run --limit 20                    # дымовой прогон: 20 строк на площадку
python -m pipeline.run --workers 4                   # не больше 4 площадок одновременно
python -m pipeline.run --no-progress                 # без живого дашборда
python -m pipeline.run --verbose                     # весь вывод скраперов в консоль
python -m pipeline.run --assemble-only               # пересобрать файлы из чекпоинтов
python -m pipeline.run --fresh                       # игнорировать чекпоинты
```

## Отслеживание прогресса

По умолчанию в консоли — живой блок, который перерисовывается на месте:

```
площадки: в работе 6 из 10 · готово 2 · ошибок 1 · прошло 12:34 · строк 44% · найдено 777
bergab.ru              █████████░░░░░░░░░░░  42%   3500/8179 найдено   148   02:41  ~04:12
podshipnik.ru          ████████████████████ 100%   8179/8179 найдено   402   08:20  готово
podshipnikru.com       ожидание
```

В строке площадки: полоска, процент, пройдено/всего строк, сколько найдено, сколько
уже идёт и оценка остатка (`~`). Площадки, которые ещё ждут свободный поток, помечены
`ожидание`; завершившиеся — `готово`, остановленные по `Ctrl+C` — `остановлено`,
упавшие — `ошибка: <причина>`.

Болтливые `print` скраперов (`Поиск`, `Варианты`, `Поиск по URL`...) в консоль больше
не попадают: каждый поток пишет в свой файл `results/logs/<site>.log`. Ошибки
скрапинга по отдельным строкам тоже уходят туда, а в конце по площадке печатается их
количество. Так дашборд остаётся читаемым, а детали всегда есть в логах.

Если stdout — не терминал (вывод в файл, консоль IDE), живой блок заменяется снимком
раз в 30 секунд: шапка со сводкой плюс строки площадок с префиксом времени.

- `--no-progress` — без дашборда, только сообщения «пройдено N строк» и итоги.
- `--verbose` — прежнее поведение: весь вывод скраперов в консоль, без лог-файлов.

## Параллельный скрапинг

Площадки сканируются параллельно: по потоку на площадку, по умолчанию — сразу все
выбранные. Работа почти целиком сетевая, поэтому потоки дают ускорение почти
пропорционально числу площадок. Состояние при этом не общее: у каждой площадки свой
экземпляр скрапера, свой чекпоинт `raw/<site>.jsonl` и свои счётчики, а входной xlsx
разбирается один раз до старта потоков.

- `--workers N` ограничивает число одновременных площадок (пригодится, если прокси или
  сами сайты не любят много параллельных запросов); `--workers 1` — прежний
  последовательный режим.
- `Ctrl+C` просит площадки завершиться после текущей строки, дожидается их и только
  потом собирает `processed.xlsx`/`unprocessed.xlsx`, поэтому чекпоинты не рвутся.
  Одна упавшая площадка не мешает остальным: её ошибка печатается, остальные
  продолжают работу.

## Что получается

```
results/
  raw/
    bergab.ru.jsonl        ← чекпоинт площадки, пополняется построчно
    etm.ru.jsonl
    ...
  logs/
    bergab.ru.log          ← весь вывод скрапера площадки (в тихом режиме)
    ...
  processed.xlsx           ← по одной лучшей записи на каждый No_
  unprocessed.xlsx         ← исходные строки, для которых ничего не принято
```

Чекпоинты дописываются после каждой найденной записи, поэтому `Ctrl+C` и повторный
запуск не теряют прогресс: уже найденные `No_` пропускаются, ненайденные пробуются снова.
`--fresh` перезаписывает чекпоинт площадки с нуля.

## Пауза и продолжение

Отдельной кнопки «пауза» нет: пауза — это `Ctrl+C`, продолжение — та же команда ещё раз.

Что делает `Ctrl+C`:

1. главный поток просит площадки остановиться. Каждая бросает работу **после текущей
   строки** — запрос к сайту не обрывается на середине;
2. найденное к этому моменту уже в чекпоинтах: запись пишется и сбрасывается на диск
   сразу после находки, поэтому пауза не оставляет «полузаписей»;
3. дождавшись потоков, пайплайн собирает `processed.xlsx`/`unprocessed.xlsx` из того,
   что есть, печатает итог по каждой площадке и выходит с кодом 130.

Продолжение — просто повторить ту же команду:

```
.venv\Scripts\python -m pipeline.run --input data.xlsx --out results
```

**Что именно пропускается.** В чекпоинте `raw/<site>.jsonl` лежат только найденные
записи. Поэтому при повторном запуске площадка пропускает строки, для которых запись
уже найдена (в дашборде это `skipped`), и заново ищет все остальные — включая те, что
уже просмотрела, но ничего не нашли. Это осознанно: «не нашлось» часто бывает сетевым
сбоем, и повторный запуск даёт второй шанс. Обратная сторона — на площадке с низкой
попадаемостью продолжение заново пройдёт уже просмотренные строки.

- `--limit N` при продолжении считает и пропущенные строки: это «просмотреть N строк
  в этом запуске», а не «найти N записей».
- `--fresh` стирает чекпоинт площадки (и её лог), площадка начинается с нуля.
- `--assemble-only` ничего не скрапит, а только пересобирает итоговые файлы из
  существующих чекпоинтов.

Итоговые xlsx всегда собираются целиком из всех чекпоинтов и входного `data.xlsx`,
а не дописываются: прерванный или упавший запуск не портит предыдущие файлы, а
заменяет их тем, что есть на диске.

Если нажать `Ctrl+C` повторно во время остановки, быстрее она не станет: главный поток
дожидается завершения текущих запросов площадок (в скраперах `requests` вызывается без
таймаута, поэтому «зависший» запрос может ждать долго). Но прерывание не отменяет
сборку: как только площадки остановятся, итоговые xlsx всё равно будут собраны.
Битая последняя строка чекпоинта (например, после выключения питания) при чтении
пропускается.

## Как выбирается победитель

Прежде чем сравнивать записи, каждая проходит проверку годности: у неё должен быть
хотя бы один ненулевой размер (`internal_d`, `external_d` или `width`). Запись, у
которой все три характеристики пустые или нулевые, **не может попасть в
`processed.xlsx` никогда** — даже при сходстве 1.0: подшипник по ней всё равно не
определить. Такие записи отбрасываются ещё при чтении чекпоинтов, поэтому они не
участвуют и в выборе победителя и не могут «затенить» нормальную запись того же
`No_` с другой площадки. В сводке их число видно строкой «без размеров (d/D/B=0)».

Для одного и того же `No_` может быть найдено несколько подходящих записей (с разных
площадок и в разных вариантах поиска). Каждая получает итоговые очки:

```
очки = bearing_similarity(source_name, description) − ZERO_PENALTY × (число нулевых d/D/B)
```

`ZERO_PENALTY = 0.05` — константа в `pipeline/assemble.py`. Нулевой или
пустой считается характеристика `internal_d`, `external_d`, `width`, равная `0`, `None`
или `NaN`. То есть запись с меньшим сходством, но полными размерами может обогнать
запись с высоким сходством и одним-двумя нулями.

Побеждает запись с максимумом очков; при равенстве — с бо́льшим числом заполненных
размеров, затем с заполненным `type`, затем с бо́льшим сходством.

Сходство пересчитывается при сборке, поэтому записи площадок, которые раньше не
записывали `bearing_similarity` (etm, arpik, podtrade, podshipnikru, consbrgs, abc_mech),
теперь тоже оцениваются. Порог `SIMILARITY_THRESHOLD = 0.85` применяется к сходству,
а не к очкам: штраф за нули влияет только на выбор победителя. Если лучший кандидат
ниже порога — строка попадает в `unprocessed.xlsx`, а не в `processed.xlsx`.

В `processed.xlsx` есть колонка `score` — те самые итоговые очки, по которым выбран
победитель (сходство остаётся в `bearing_similarity`).

## Зависимости и ограничения

- Входной xlsx должен содержать `No_` и `Description`; `Blocked` подставляется пустым,
  если его нет.
- Варианты поиска берутся из `compare/имена_без_русских_слов_v3.xlsx` (колонки
  `Description` / `Search`, варианты через ` | `). Если описания нет в мэппинге,
  строка не ищется и уходит в `unprocessed.xlsx`; в логе будет счётчик
  «без вариантов поиска».
- Площадки регистрируются в `pipeline/registry.py` — новая площадка = одна строка.
- Прокси по умолчанию: `HTTP_PROXY` и `HTTPS_PROXY` = `http://172.31.24.36:8090`
  (выставляются в `scrapper/net.py` при создании скрапера). Если переменные окружения
  уже заданы, используются они — прокси можно переопределить перед запуском.
- единственная точка входа — `python -m pipeline.run`. Старые ручные скрипты
  (`main*.py`, `merge/merge_results.py`, `merge/merge_copyes.py`, `split/*.py`,
  `reprocess/reprocess.py`, `data/v1/separate.py`) удалены: дедупликация и выбор
  записи теперь здесь, в `pipeline/assemble.py`. При необходимости файл можно
  достать из истории git (`git checkout a1eb204 -- <путь>`).
