# Пайплайн скрапинга

Одна команда проходит по нескольким площадкам и собирает **два** итоговых файла:
`processed.xlsx` (найденные цепи) и `unprocessed.xlsx` (то, что не нашли).

## Запуск

Из корня проекта:

```
.venv\Scripts\python -m pipeline.run --input data.xlsx --out results
```

Полезные варианты:

```
python -m pipeline.run --list-sites                  # какие площадки известны
python -m pipeline.run --sites aksdekom,ntg      # только выбранные
python -m pipeline.run --limit 20                    # дымовой прогон: 20 строк на площадку
python -m pipeline.run --workers 4                   # не больше 4 площадок одновременно
python -m pipeline.run --no-progress                 # без живого дашборда
python -m pipeline.run --verbose                     # весь вывод скраперов в консоль
python -m pipeline.run --assemble-only               # пересобрать файлы из чекпоинтов
python -m pipeline.run --fresh                       # игнорировать чекпоинты
```

## Отслеживание прогресса

По умолчанию в консоли — живой блок, который перерисовывается на месте:

```
площадки: в работе 3 из 3 · готово 1 · ошибок 0 · прошло 05:12 · строк 44% · найдено 777
aksdekom               █████████░░░░░░░░░░░  42%   3500/8179 найдено   148   02:41  ~04:12
ntg                    ████████████████████ 100%   8179/8179 найдено   402   08:20  готово
euromehanika           ожидание
```

В строке площадки: полоска, процент, пройдено/всего строк, сколько найдено, сколько
уже идёт и оценка остатка (`~`). Площадки, которые ещё ждут свободный поток, помечены
`ожидание`; завершившиеся — `готово`, остановленные по `Ctrl+C` — `остановлено`,
упавшие — `ошибка: <причина>`.

Болтливые `print` скраперов (`Поиск`, `Варианты`, `Поиск по URL`...) в консоль больше
не попадают: каждый поток пишет в свой файл `results/logs/<site>.log`. Ошибки
скрапинга по отдельным строкам тоже уходят туда, а в конце по площадке печатается их
количество. Так дашборд остаётся читаемым, а детали всегда есть в логах.

Если stdout — не терминал (вывод в файл, консоль IDE), живой блок заменяется снимком
раз в 30 секунд: шапка со сводкой плюс строки площадок с префиксом времени.

- `--no-progress` — без дашборда, только сообщения «пройдено N строк» и итоги.
- `--verbose` — прежнее поведение: весь вывод скраперов в консоль, без лог-файлов.

## Параллельный скрапинг

Площадки сканируются параллельно: по потоку на площадку, по умолчанию — сразу все
выбранные. Работа почти целиком сетевая, поэтому потоки дают ускорение почти
пропорционально числу площадок. Состояние при этом не общее: у каждой площадки свой
экземпляр скрапера, свой чекпоинт `raw/<site>.jsonl` и свои счётчики, а входной xlsx
разбирается один раз до старта потоков.

- `--workers N` ограничивает число одновременных площадок (пригодится, если прокси или
  сами сайты не любят много параллельных запросов); `--workers 1` — прежний
  последовательный режим.
- `Ctrl+C` просит площадки завершиться после текущей строки, дожидается их и только
  потом собирает `processed.xlsx`/`unprocessed.xlsx`, поэтому чекпоинты не рвутся.
  Одна упавшая площадка не мешает остальным: её ошибка печатается, остальные
  продолжают работу.

## Что получается

```
results/
  raw/
    aksdekom.jsonl         ← чекпоинт площадки, пополняется построчно
    ntg.jsonl
    ...
  logs/
    aksdekom.log           ← весь вывод скрапера площадки (в тихом режиме)
    ...
  processed.xlsx           ← по одной лучшей записи на каждый номер
                              (колонки и оформление как у входного xlsx)
  unprocessed.xlsx         ← исходные строки, для которых ничего не принято
```

Чекпоинты дописываются после каждой найденной записи, поэтому `Ctrl+C` и повторный
запуск не теряют прогресс: уже найденные номера пропускаются, остальные пробуются снова.
`--fresh` перезаписывает чекпоинт площадки с нуля.

## Пауза и продолжение

Отдельной кнопки «пауза» нет: пауза — это `Ctrl+C`, продолжение — та же команда ещё раз.

Что делает `Ctrl+C`:

1. главный поток просит площадки остановиться. Каждая бросает работу **после текущей
   строки** — запрос к сайту не обрывается на середине;
2. найденное к этому моменту уже в чекпоинтах: запись пишется и сбрасывается на диск
   сразу после находки, поэтому пауза не оставляет «полузаписей»;
3. дождавшись потоков, пайплайн собирает `processed.xlsx`/`unprocessed.xlsx` из того,
   что есть, печатает итог по каждой площадке и выходит с кодом 130.

Продолжение — просто повторить ту же команду:

```
.venv\Scripts\python -m pipeline.run --input data.xlsx --out results
```

**Что именно пропускается.** В чекпоинте `raw/<site>.jsonl` лежат только найденные
записи. Поэтому при повторном запуске площадка пропускает строки, для которых запись
уже найдена (в дашборде это `skipped`), и заново ищет все остальные — включая те, что
уже просмотрела, но ничего не нашли. Это осознанно: «не нашлось» часто бывает сетевым
сбоем, и повторный запуск даёт второй шанс. Обратная сторона — на площадке с низкой
попадаемостью продолжение заново пройдёт уже просмотренные строки.

- `--limit N` при продолжении считает и пропущенные строки: это «просмотреть N строк
  в этом запуске», а не «найти N записей».
- `--fresh` стирает чекпоинт площадки (и её лог), площадка начинается с нуля.
- `--assemble-only` ничего не скрапит, а только пересобирает итоговые файлы из
  существующих чекпоинтов.

Итоговые xlsx всегда собираются целиком из всех чекпоинтов и входного `data.xlsx`,
а не дописываются: прерванный или упавший запуск не портит предыдущие файлы, а
заменяет их тем, что есть на диске.

Если нажать `Ctrl+C` повторно во время остановки, быстрее она не станет: главный поток
дожидается завершения текущих запросов площадок (в скраперах `requests` вызывается без
таймаута, поэтому «зависший» запрос может ждать долго). Но прерывание не отменяет
сборку: как только площадки остановятся, итоговые xlsx всё равно будут собраны.
Битая последняя строка чекпоинта (например, после выключения питания) при чтении
пропускается.

## Как выбирается победитель

Прежде чем сравнивать записи, каждая проходит проверку годности: у неё должен быть
хотя бы одна ненулевая характеристика цепи из `ChainScrapperMapper.DIMENSIONS` —
шаг, диаметры валика и ролика, длина валика, высота пластины, расстояние между
пластинами. Запись, у которой все характеристики пустые или нулевые, **не может
попасть в `processed.xlsx` никогда** — даже при сходстве 1.0: цепь по ней всё равно
не определить. Такие записи отбрасываются ещё при чтении чекпоинтов, поэтому они не
участвуют и в выборе победителя и не могут «затенить» нормальную запись того же
номера с другой площадки. В сводке их число видно строкой «без характеристик (все 0)».

Для одного и того же номера (`ChainData['id']`, колонка «Номер материала») может быть
найдено несколько подходящих записей (с разных площадок и в разных вариантах поиска).
Каждая получает итоговые очки:

```
сходство = max(сходство(source_name, link), сходство(source_name, full_link))
очки = сходство − ZERO_PENALTY × (число пустых характеристик)
```

`ZERO_PENALTY = 0.05` — поле маппера модели (`ChainScrapperMapper.ZERO_PENALTY`).
Нулевой или пустой считается характеристика цепи, равная `0`, `None` или `NaN`. То
есть запись с меньшим сходством, но полными характеристиками может обогнать запись
с высоким сходством и одним-двумя нулями.

И сходство, и очки считает сам скрапер и пишет их в запись: `name_similarity` —
в `scrap_list` при выборе кандидата, `score` — в `Scrapper.scrap` сразу после того,
как площадка отдала характеристики. В чекпоинте `raw/<site>.jsonl` они уже лежат
готовыми, поэтому сборка их не пересчитывает, а только читает. У записей старых
чекпоинтов, где этих полей не было, сборка досчитывает их сама.

Побеждает запись с максимумом очков; при равенстве — с бо́льшим числом заполненных
характеристик, затем с бо́льшим сходством.

Сходство имён цепей считает `ChainScrapperMapper._name_similarity`: общий
`ScrapperMapper.name_similarity` убирает из `link` и `full_link` бренд и
сравнивает найденное имя с обеими строками, беря большее сходство. Метод
принимает найденное имя и запись `EntityData`, а нужные поля достаёт из неё
сам. Дальше сравнивается не текст названия, а обозначение цепи, поэтому
описательные слова, ГОСТ-аналог в скобках и бренд на результат не влияют.

Обозначения разных систем приводятся к одному ключу (`chain_markings`), так что
одна и та же цепь совпадает, в какой бы системе её ни записали:

| запись | ключ |
|---|---|
| `06B-1` | `ISO:06B`, 1 ряд |
| `ПР-9,525-9,1` | `ISO:06B`, 1 ряд (шаги ГОСТ 13568 = серия B) |
| `ПРД-12,7-36` | `ISO:08B`, 2 ряда (ПРД двухрядная) |
| `ANSI 40-2`, `40-2` | `ISO:08A`, 2 ряда (#40 и 08A — одна цепь) |
| `#35` | `ANSI:35`, 1 ряд (пары в серии A нет) |

Совпало обозначение — `1.0`, не совпало — `0.0`. Грузоподъёмность ГОСТ (второе
число, `-9,1`) в ключ не входит: обозначение ISO её тоже не различает. Слово
«Звездочка» или «Звено» в названии с тем же обозначением даёт `0.0` — это не цепь.

Если обозначения нет, сравниваются номера-артикулы («5592312.100»): равные дают
`1.0`, похожие — не больше `CHAIN_NUMBER_CEILING = 0.80`, чтобы другой артикул не
прошёл порог. Когда в названии нет ни обозначения, ни номера, работает базовое
сравнение строк из `ScrapperMapper._name_similarity`.

Сходство считается при скрапинге и лежит в чекпоинте готовым: для каждой пары
«найденное имя — `link`» и «найденное имя — `full_link`» считается своё значение,
в запись идёт большее. Перед сравнением из обеих строк убирается `brand`; из
найденного имени он не удаляется. Порог `SIMILARITY_THRESHOLD = 0.85`
применяется к сходству, а не к очкам: штраф за нули влияет только на выбор
победителя. Если лучший кандидат ниже порога — строка попадает в
`unprocessed.xlsx`, а не в `processed.xlsx`.

`name_similarity` и `score` — служебные поля записи: они есть в `ChainData`,
пишутся в чекпоинт `raw/<site>.jsonl` и по ним выбирается победитель, но в
итоговые xlsx не попадают. Набор колонок у входного и выходных файлов одинаковый:
`processed.xlsx` повторяет заголовки и порядок колонок входного xlsx
(`ChainScrapperMapper.COLUMN_TITLES`, метод `to_row`), а `unprocessed.xlsx` — это
необработанные строки входа как есть.

Оформление тоже переносится со входного файла (`utils/excel.py`, `copy_style`):
ширины и видимость колонок, шрифт и заливка шапки, оформление обычных строк,
формат чисел, закреплённая шапка и автофильтр. Колонки сопоставляются по заголовкам,
так что порядок в файлах может отличаться. Оформление строк берётся из первой строки
данных входа — если в исходной таблице строки размечены по-разному, различия не
сохранятся.

## Модель данных и маппер

`pipeline/assemble.py` не знает, что собирает цепи: модель данных приходит в него
маппером (`assemble(input_path, raw_dir, out_dir, mapper)`), и всё специфичное
берётся из него:

| что нужно сборке | откуда в маппере |
|---|---|
| что считать характеристикой и за что снимать очки | `DIMENSIONS`, `ZERO_PENALTY` |
| колонки входа и выхода, их порядок и заголовки | `COLUMN_TITLES` (из него же `COLUMNS`) |
| по какой колонке искать строку во входе | `KEY_FIELD` → `key_column` |
| ключ записи | `key(record)` |
| сходство, очки, годность записи | `name_similarity`, `score`, `has_dimensions` |
| строка итогового xlsx | `to_row` |

Сейчас в `pipeline/run.py` подставляется `ChainScrapperMapper` — единственный
полностью подключённый маппер. Заготовки для ремней, шлангов и лент лежат в
`scrapper/belts`, `scrapper/hoses` и `scrapper/tapes`: у них уже работают
`get_name_variants` и общее сходство по `link`/`full_link`, но модели данных
и подключение к пайплайну появятся позже.

## Проверка браузера (антибот)

`euromehanika.ru` отдаёт вместо HTML-страницы заглушку «Проверяем поддержку браузера...»
со статусом 200 и пускает дальше только после исполнения её JavaScript: без cookie в
ответе нет ни разметки каталога, ни карточки товара, и площадка «молча» ничего не
находит. `cloudscraper` тут не помогает — он умеет обходить только Cloudflare, а
заглушки других антиботов возвращает как обычную страницу.

Проверку проходим один раз вручную, в браузере, и переиспользуем полученные cookie:

1. открыть `https://euromehanika.ru/` в браузере и дождаться каталога;
2. F12 → Network → любой запрос → Request Headers → скопировать значение `Cookie`
   целиком (`PHPSESSID=...; pa_js_passed=...; ...`);
3. вставить строку в константу `COOKIES` в
   `scrapper/chains/implementation/euromehanika_scrapper.py` либо задать переменную
   окружения `EUROMEHANIKA_COOKIE`:

   ```
   set EUROMEHANIKA_COOKIE=PHPSESSID=...; pa_js_passed=...
   ```

   При запуске из IDE надёжнее константа: в cookie встречаются `%` и `$`, а `set` в
   cmd и подстановка в PowerShell могут их испортить. В PowerShell, если всё же
   задаёте переменную, берите значение в одинарные кавычки:
   `$env:EUROMEHANIKA_COOKIE='...'`.

Ключевые cookie — `pa_js_passed` (подписанный токен «проверка пройдена») и
`PHPSESSID`; остальные (`_ym_*`, `_ga*`, `BITRIX_SM_*`) — аналитика и сессия Битрикса,
они не нужны, но и не мешают.

Cookie живут ограниченное время и обычно привязаны к IP и User-Agent. Когда протухнут,
в логе площадки появится ошибка «проверка браузера вернулась и с cookie» — скопируйте
свежую строку из браузера. Скрапер ходит через тот же прокси, что и браузер, а UA в
`Scrapper.headers` — Yandex Browser; если копируете cookie из другого браузера,
поменяйте UA на его.

## Зависимости и ограничения

- Входной xlsx читает `ChainScrapperMapper.from_row`: нужны колонки «Номер материала»
  (она же `id` записи и ключ чекпоинта), «Ссылка», «Полное наименование внутреннее»,
  «Номер детали производителя», «Производитель/Марка/Бренд», «Модель» и характеристики
  цепи («Шаг цепи мм», «Диаметр валика мм» и т.д.).
- Варианты поиска строит `ChainScrapperMapper.get_name_variants` — из полного
  наименования, «Ссылки», номера детали и бренда; в файлах мэппинга они больше не
  берутся. Полное наименование дополнительно укорачивается с конца
  (`_tail_variants`): «Цепь 06B-1 D3 DH» → «Цепь 06B-1 D3» → «Цепь 06B-1», чтобы
  запрос совпал с заголовком площадки, где хвостовых уточнений («EMT», «5 м»,
  ГОСТ-аналог в скобках) может не быть. Вариант берётся, пока в нём остаётся
  цифра, — иначе запрос уже не про цепь; всего не больше
  `TAIL_VARIANTS_LIMIT = 4` укорочений.
- Из полного наименования отбрасываются и русские описательные слова
  (`_drop_russian_words`): «Цепь роликовая приводная 06B-1 D3 DH» →
  «Цепь 06B-1 D3 DH». Остаются слово «Цепь» и всё, что содержит цифры —
  кириллическое обозначение вроде «ПР-9,525-9,1» тоже сохраняется. Если после
  отбрасывания в названии не осталось цифр, вариант не добавляется.
- Площадки регистрируются в `pipeline/registry.py` — новая площадка = одна строка.
- Прокси по умолчанию: `HTTP_PROXY` и `HTTPS_PROXY` = `http://172.31.24.36:8090`
  (выставляются в `scrapper/net.py` при создании скрапера). Если переменные окружения
  уже заданы, используются они — прокси можно переопределить перед запуском.
- единственная точка входа — `python -m pipeline.run`. Старые ручные скрипты
  (`main*.py`, `merge/merge_results.py`, `merge/merge_copyes.py`, `split/*.py`,
  `reprocess/reprocess.py`, `data/v1/separate.py`) удалены: дедупликация и выбор
  записи теперь здесь, в `pipeline/assemble.py`. При необходимости файл можно
  достать из истории git (`git checkout a1eb204 -- <путь>`).
